# Vognary Leap Plan — architecture, gaps, and the wow ladder (2026-07-20)

This is the execution map for taking Vognary from "gate-green and honest" to
"crowd-ready with a wow a first-time visitor feels in under a minute." It is
written so any agent can pick up a work package cold: every package names its
files, the utilities to reuse, acceptance criteria, and the command that proves
it. Read Part 0 before touching anything.

---

## Part 0 — Invariants every agent must obey

1. **Work in an isolated git worktree** cut from the freshest committed HEAD
   (`git worktree add ../Vognary-<slug> -b <branch> <sha>`). Multiple agents
   edit this repo concurrently; never work in a checkout with someone else's
   dirty files. Check `git status` in the main checkout first and treat every
   dirty file there as off-limits.
2. **The brand is fixed.** Nakul the mongoose, Fraunces display, graphite/gold.
   Deepen, never swap (`docs/` brand kit, `/brand` route).
3. **Honesty language is machine-enforced.** Merchants are *watched*, never
   *linked* (`scripts/check-public-claims.mjs` fails the build on violations).
   Rails/sources use *connect* voice. Never write copy that claims more than
   the deployment proves; the `*_STATUS=""` env-attestation pattern is the
   product's spine, not an inconvenience.
4. **Scoring is minimum-row** (`docs/path-to-10.md`): the composite equals the
   weakest row. Always ask "does this raise the lowest row?" before building.
5. **Gates before merge:** `npm run lint && npm run typecheck &&
   npm run claims:check && npm test`, then `npm run build && npm run
   perf:budget`. UI journeys: the signed-in e2e recipe in
   `.github/workflows/ci.yml` (dev server + development login). The perf
   ceilings (214.8 KB JS on `/`, `/app`, `/verify`) are hard; WOW packages
   must fit inside them.

## Part 1 — The architecture as it stands (how we got here)

Vognary is an evidence-first recurring-money audit for the Indian market,
built guest-first with a fail-closed activation model. Five layers:

1. **Guest engine (client-only, stateless).** `src/lib/receipt-parser.ts`,
   `recurring-audit.ts`, `renewal-timeline.ts`, `suggested-cuts.ts`,
   `sample-audit.ts` run entirely in the browser tab.
   `src/app/guest-audit-client.tsx` is the surface. Nothing leaves the tab;
   this is why the product scales to a crowd on day one — the first-value path
   costs the server nothing.
2. **Signed-in workspace.** `src/app/vognary-mvp-client.tsx` (5.5k lines — the
   known monolith) over raw Postgres (`infra/postgres/`, ~40 store modules in
   `src/lib/server/`), custom auth (signed cookies + magic link + Google OIDC
   + prod-disabled dev login), AES-256-GCM token vault, encrypted workspace
   snapshots.
3. **Connect rails.** Registry + honesty taxonomy (`src/lib/connectors.ts`,
   `connect-rails.ts`, `connector-runtime.ts`), adapters for Gmail read-only,
   Setu AA, AWS/OpenAI/Anthropic costs. Real first sync is gated on founder
   externals (Google verification G-A, Setu sandbox G-B, FIU/TSP G-C).
4. **Money + ops.** Fail-closed Razorpay checkout (hidden until legal/KYC
   attestations), secret-gated internal cron routes (sync, retention, renewal
   alerts, savings verification), backup + restore-drill readiness, shared
   Postgres rate limiting.
5. **The gate wall.** claims/brand/research checks, statement/receipt corpus
   gates (waiting on real consented fixtures), perf + Lighthouse budgets,
   71+ unit test files, 9 Playwright specs with axe, `release:gate`
   orchestrator (in flight from a parallel session), and — as of this branch —
   PR CI that actually runs typecheck/research/brand and the four signed-in
   journeys, live trust signals on `/security` and `/beta-readiness`, and the
   founder dependency chain in `docs/founder-activation-checklist.md`.

The defining design decision across all five: **nothing claims what is not
proven.** Blank env renders "Not yet proven"; checkout stays hidden; connector
states tell the truth. This is rare enough in fintech to be the wow — if we
surface it right (Part 3).

## Part 2 — What is genuinely lacking

### A. Founder-owned blockers (no code can fix; already runbooked)
Google G-A, Setu G-B, FIU/TSP G-C, ≥100/≥200 consented corpora, Razorpay KYC +
legal, Resend verification, infra attestations, canary. Ordered chain with
proof commands: `docs/founder-activation-checklist.md`. These bound the
composite score; every agent-hour spent elsewhere should raise a row that
does not depend on them.

### B. Product gaps that mute the launch-day wow
1. **Time-to-wow is not on the landing page.** The guest engine is client-side
   and instant, but a cold visitor must click through to `/app` and figure out
   pasting. The single highest-leverage move in the repo: put the first result
   *on* the landing (WOW-1).
2. **The sample audit is passive.** "See a sample" seeds data but nobody
   narrates why it matters. Nakul exists as a brand system and is underused as
   a guide (WOW-2).
3. **No collective proof surface.** Verified savings + proof-graph + the
   public pack verifier exist, but the landing shows no aggregate, verifiable
   "this is what Vognary has actually found" wall (WOW-3).
4. **Mobile capture friction.** The PWA installs, but receipts live in email
   and screenshots on phones; there is no share-sheet path into the audit
   (WOW-4).
5. **Nothing pulls a guest back.** The audit ends with insight but no artifact
   that re-surfaces at the right moment — the renewal date (WOW-5).
6. **No funnel eyes.** `api/product-events` ingests, but nothing analyzes;
   launch day will be flown blind. (C-2.)

### C. Engineering leverage gaps
1. **`vognary-mvp-client.tsx` monolith** (5,484 lines) — the biggest brake on
   parallel agent velocity. Decompose only in a quiet window (it conflicts
   with everything); split by workspace section into `src/app/workspace/*`.
2. **Product-events analysis job**: a small secret-gated summary route +
   founder digest (counts by event type, funnel steps, day-over-day) —
   env-only infra, no third party.
3. **Small-fixes queue** (each ≤30 min, safe any time):
   - "Link a source / Link live sources" rail copy in
     `vognary-mvp-client.tsx` (empty-state sidebar) and `guide/page.tsx` →
     connect voice.
   - `next.config.ts` `devIndicators.position` — the "avatar over detail
     sheet" worklog bug is the **dev-tools indicator** (proven: elementFromPoint
     → `NEXTJS-PORTAL`, no app element ≥ z-70); close the worklog item.
   - `.env.example`: drop unwired Clerk vars; add dated
     `BACKUP_RESTORE_DRILL_AT` attestation and surface it in
     `src/lib/server/trust-signals.ts`.
   - `eslint-plugin-jsx-a11y` recommended set in `eslint.config.mjs`.
   (All were parallel-locked on 2026-07-20; re-check `git status` first.)

## Part 3 — The Wow Ladder (the plan)

**Design principle:** the wow must land inside 60 seconds, work for a crowd,
require zero trust, and be provable — because "measured, not promised" is the
product's identity. Every package below is honest-by-construction: it renders
only from real local computation or real verified records.

### WOW-1 — The landing does the audit (highest leverage, do first)
**Goal:** a visitor pastes one receipt into the hero of `/` and watches the
ledger materialize in place — burn, next renewal, one action — before any
navigation, login, or cookie.
**Low-level:**
- Extract the paste→parse→result core from `guest-audit-client.tsx` into
  `src/app/instant-audit.tsx` (client component; reuses
  `receiptTextToManualInputs` from `src/lib/receipt-parser.ts` and the
  audit derivation from `src/lib/recurring-audit.ts`).
- Render compact in `src/app/page.tsx` hero behind `next/dynamic` (landing
  LCP budget is sacred — the static hero paints first, the paste box hydrates
  after; keep added JS inside the 214.8 KB ceiling, measured by
  `npm run perf:budget`).
- "Continue in the full audit" hands off via the existing
  `guestAuditTransferKey` sessionStorage contract (see
  `guest-audit-client.tsx` transfer effect) so nothing is retyped.
- Copy passes `claims:check`; one sample-receipt chip ("try a sample receipt")
  for visitors with nothing to paste, reusing `sampleReceiptText` from
  `src/lib/sample-audit.ts`.
**Accept:** paste → result < 3s client-side with no network calls; perf:budget
and Lighthouse hold on `/`; axe serious/critical = 0; new e2e spec
`tests/e2e/landing-instant-audit.spec.ts` (guest project, no login env).

### WOW-2 — Nakul walks the sample (the demo that sells the ledger)
**Goal:** "Watch a 20-second audit" on `/` and in the signed-in empty state:
a scripted, reduced-motion-safe sequence where Nakul narrates the existing
sample audit — evidence in, ledger out, one suggested cut, proof chip open.
**Low-level:** `src/app/nakul-demo.tsx` stepping through the real sample data
(`src/lib/sample-audit.ts`) with the existing pose system (`src/app/character.tsx`)
and `client-motion.ts` (respects `prefers-reduced-motion`; the
`reduced-motion.spec.ts` pattern shows how to test it). No video, no external
assets — it composes the real components, so it can never drift from the
product.
**Accept:** plays fully with reduced-motion (as stepped stills); adds zero JS
to the initial landing chunk (dynamic import on interaction); e2e asserts the
final frame shows the sample ledger.

### WOW-3 — The proof wall (collective savings, verifiable)
**Goal:** a landing section: "₹X verified savings across N audits — every
rupee traceable," where X and N come only from real verified-savings records,
and each entry links to the public pack verifier (`/verify`).
**Low-level:** server route segment on `/` (or a `force-dynamic` fragment via
Suspense) reading an aggregate from `src/lib/server/` verified-savings /
proof-graph stores (add `getPublicSavingsAggregate()` — count + sum of
*verified* records only, no user data). Fail-closed: when the DB is absent or
the count is 0, render "Verified counting starts at launch — here is how
verification works" linking `/verify`. Copy must survive the stricter
`claims:check`.
**Accept:** blank env renders the honest empty state; with seeded verified
records the numbers appear; unit test for the aggregate; no PII in output
(assert fields in test).

### WOW-4 — Share a receipt from any app (PWA share target)
**Goal:** on Android/desktop-PWA, "Share → Vognary" on any receipt email/text
drops it straight into the guest audit — no account, no upload UI.
**Low-level:** add `share_target` to `src/app/manifest.ts` (POST,
`text/plain` + `title`/`text` params; cast if `MetadataRoute.Manifest` lacks
the field), handler route `src/app/share/route.ts` that stores the shared text
under the existing `guestAuditTransferKey` contract via a tiny redirect page,
then opens `/app`. iOS lacks share_target — feature-detect and keep the
paste path primary in copy.
**Accept:** manifest validates (Lighthouse PWA pass holds); e2e simulates the
POST and asserts the guest audit hydrates the shared text; copy honest about
platform support.

### WOW-5 — The renewal that comes back (calendar artifact)
**Goal:** every guest audit ends with "Add your next renewal to your
calendar" — a client-generated `.ics` (zero backend, zero account) whose event
description links back and names the amount and merchant the user themselves
proved. The wow lands twice: once now, once the day before the charge.
**Low-level:** `src/lib/ics.ts` (pure function, unit-tested: VCALENDAR/VEVENT
with VALARM -P1D, proper escaping/CRLF/UTC) + a button in the guest result
panel (and detail sheet later — monolith, minimal additive edit only). Use
the earliest upcoming renewal from `buildRenewalTimeline`.
**Accept:** generated file imports cleanly (validate structure in unit test);
button appears only when a dated renewal exists; no network calls.

**Sequencing:** WOW-1 first (it multiplies everything else), then 3 and 5 in
parallel (disjoint files), then 2, then 4. C-2 (funnel eyes) alongside any of
them. The monolith decomposition (C-1) waits for a quiet window and its own
branch; do not attempt it while WOW packages are open.

## Part 4 — Execution protocol per package

For each package: cut a worktree → build → run the Part 0 gate chain → prove
the acceptance criteria with the named spec/command → append evidence to the
PR description (not to parallel-locked docs) → PR against `main` titled
`feat(wow-N): <goal>`. One package per branch; no cross-package edits to the
same file. If a needed file is dirty in the main checkout, stop and flag it
in the PR/handoff note instead of editing it.
